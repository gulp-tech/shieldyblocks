## 2. Регистрация и согласованный мост между classloader

При запуске плагина только при `experimental-bedrock-visual.enabled: true` в `plugins/HyperTNT/config.yml` `BukkitVisualBridge.start()` регистрирует `mk.hypertnt.visual.VisualSource` через `Bukkit.getServicesManager().register(VisualSource.class, source, plugin, ServicePriority.Normal)`. Это реальная регистрация класса, загруженного classloader плагина. API и формат нестабильны, версия схемы в JAR явно не объявлена.

**Договорённый вариант для эксперимента с этим конкретным JAR:** извлечь регистрацию самого плагина по объекту владельца, не подключая и не копируя классы API в ядро; вызвать публичные методы и декодировать records через рефлексию. Пример поиска, выполнять в разрешённом потоке платформы:

```java
Plugin plugin = Bukkit.getPluginManager().getPlugin("HyperTNT");
Object source = null;
Class<?> serviceType = null;
if (plugin != null && plugin.isEnabled()) {
    for (RegisteredServiceProvider<?> r :
            Bukkit.getServicesManager().getRegistrations(plugin)) {
        if (r.getPlugin() == plugin
                && r.getPriority() == ServicePriority.Normal
                && r.getService().getName().equals("mk.hypertnt.visual.VisualSource")
                && r.getService().isInstance(r.getProvider())) {
            if (source != null) throw new IllegalStateException("ambiguous source");
            source = r.getProvider();
            serviceType = r.getService();
        }
    }
}
// source == null: подключение пока невозможно; не использовать подмены.
// Object connection = serviceType.getMethod("connect").invoke(source);
```

Проверять JAR/версию, публичные методы и форму возвращаемых records, обрабатывать `InvocationTargetException` и несовпадение контракта fail-closed. Код примера поиска через Bukkit — **эскиз**, не тестировался на настоящем сервере. Нельзя использовать `load(VisualSource.class)`, где `VisualSource.class` — копия класса из classloader ядра: идентичность отличается. В изолированном тесте JAR загружался через `URLClassLoader`, после чего вызываются его публичные record-методы; сам поиск регистрации через Bukkit там не проверялся и совместимость classloader настоящего сервера не подтверждена.

На регистрацию/деактивацию сервиса или плагина: перед подключением удалить предыдущие подмены, закрыть старую подписку и получить новый снимок; на закрытие удалить подмены и освободить ссылки на provider, records, Methods и classloader. События регистрации в конкретном ядре проверить; добавить ограниченный повторный поиск при позднем старте. Если регистрация есть, но `connect()` бросает исключение, источник может уже быть закрыт: не использовать и не зацикливать подключение (в текущем коде ошибка отложенного `flush` закрывает источник, но не обязательно снимает регистрацию до отключения плагина).

Для реально стабильного API нужно отдельно договориться о версии схемы/возможностей и общей, единожды загруженной API-библиотеке в совместном parent classloader; не вшивать отдельные копии DTO по обе стороны. Текущая сборка этого не предоставляет, поэтому нельзя объявлять мост стабильным.

## 3. Карантин и восстановление

При обнаруженной поздней отмене или ошибке проверки отмены в конце тика текущий источник добавляет **все чанки общей отложенной группы** в in-memory `quarantined`, оставляет их неизвестными и предупреждает в логе. `refreshChunk` на них возвращает `false`. Публичного метода снять карантин нет; `/hypertnt reload` и выгрузка/загрузка чанка не снимают его. Закрытие и новый запуск плагина создают новый источник с пустым карантином, **но это не доказывает правильность реестра**: поздно отменённое событие могло уже изменить игровой реестр, а обычный TNT и кастомный имеют одинаковый материал.

До нового метода: на тестовой копии сохранить резервную копию, остановить сервер, независимо проверить/исправить состояние мира и реестра по надёжным данным владельца, затем запустить и заново подключиться. Если тип не известен достоверно, не угадывать его и не показывать подмену; ядро не снимает карантин самостоятельно. После перезапуска без подтверждённой сверки нельзя считать состояние безопасным.

Для будущего API предложить отдельное явно авторизованное действие: подтверждённая **авторитетная** сверка реестра и мира, устранение гонок с событиями, журналирование и только затем снятие конкретного карантина с публикацией полного проверенного состояния. Обычного `getType() == TNT` недостаточно для доказательства типа. В текущий JAR такой механизм не добавлен.

## 4. Изменения другими плагинами

Наблюдаются стандартные события установки/ломания/горения/поршня/взрыва и жизненного цикла чанка; прямой поджог внутри HyperTNT отмечается отдельно. Произвольная правка блоков другим плагином **без события не обнаруживается**. Периодическая проверка материала обнаружит часть несовпадений, но не докажет замену `TNT → обычный TNT` в той же позиции.

Нужен согласованный вызывающий механизм: до неизвестного пакетного изменения одним вызовом `invalidateChunks` отметить все затронутые чанки, затем после надёжного завершения и исправления/проверки авторитетного реестра запросить `refreshChunk` только для уже загруженных чанков. При ошибке оставлять unknown. Изменяющая сторона обязана сообщить точный полный набор чанков, включая перемещение через границу; если набор неизвестен, безопаснее снять все подмены затронутой области/источника и начать resync. Нельзя только наблюдать тип блока и объявлять реестр достоверным.

Внимание: нынешний `invalidateChunks` не создаёт межоперационную блокировку (`begin/end`), `refreshChunk` может быть вызван до окончания внешней операции. Поэтому соглашение о сериализации на главном потоке и запрет reentrant refresh обязательны; для произвольных асинхронных/не сотрудничающих изменений поддержки пока нет. Один hook после commit не устраняет окно до commit: требуется предынвалидация или блокировка показа и post-commit/abort сигнал. Передавать объединение чанков всех источников и назначений, уничтоженных/заменённых координат, с UUID каждого мира; при неизвестном полном наборе fail-closed для соответствующего источника/области. Реализация этих hooks ещё не готова.

## 5. Reload, остановка, epoch, ревизии и переполнение

- `/hypertnt reload` перезагружает конфиги типов и инвалидирует текущие known-чанки. Сам источник, подписки и epoch сохраняются; может идти ожидающий пересчёт. Потребитель обрабатывает invalidation и запрашивает повторную сверку нужных загруженных чанков. Флаг `experimental-bedrock-visual.enabled` читается при запуске, изменение флага через reload не подключает и не отключает источник.
- При штатном отключении плагина `source.close()` даёт существующим подпискам `CLOSED`, затем производится снятие сервиса; требуется убрать все визуальные подмены и освободить ссылки. В аварийных случаях нельзя полагаться исключительно на событие снятия сервиса; необходима обработка `CLOSED` и сбоя связи.
- Новый объект источника создаёт случайный UUID `epoch`, `revision` начинается с 0 и увеличивается при фактическом изменении представления. Начальный снимок при включении может уже иметь revision > 0. Подписка и снимок из `connect()` согласованы под одной блокировкой. Сверять последовательность revision **глобально до фильтрации чанков**. Другой epoch, пропущенная/повторная ревизия, ошибка декодирования или `RESYNC_REQUIRED`: удалить подмены, закрыть подписку, с ограниченным backoff получить полный новый снимок и подписку. Устаревшие асинхронные результаты от прежнего подключения/epoch отвергать.
- `chunkSnapshot` — частичный снимок, но с глобальной revision; он не заменяет глобальный снимок. Надо буферизовать поток и правильно совместить по revision, не откатывать состояние поздним ответом; если это нельзя гарантировать — полный reconnect.
- При `Poll.state() == OK` поле `batch()` может быть `null` (очередь пуста). При `RESYNC_REQUIRED` и `CLOSED` полезного batch нет.

## 6. Лимиты и понятие unknown

У конкретного `RegistryVisualPublisher` очередь — **256 пакетов на каждую подписку**. При попытке добавить 257-й непрочитанный пакет существующая очередь очищается и выставляется `RESYNC_REQUIRED`; эта подписка больше не выдаёт дельты, нужен новый `connect()`. `VisualFeed` как отдельный класс принимает размер очереди в конструкторе, но опубликованный сервис создаёт его с 256.

Ограничения на число позиций/чанков в одном batch, размер полного снимка, количество подписок, число записей реестра и суммарный размер данных в байтах в текущем источнике **не заданы**. Лимит на 256 пакетов не является лимитом памяти; крупный batch или snapshot может быть большим.

**Предложение начальных настраиваемых ограничений для тестовой копии, а не уже действующие лимиты или подтверждённая производительность:**

| Значение | Начальный предел |
| --- | ---: |
| `snapshot.entries` | 100 000 позиций |
| `snapshot.knownChunks` | 32 768 чанков |
| `batch.upserts.size + batch.removals.size` | 16 384 позиции |
| `batch.known.size + batch.unknown.size` | 4 096 чанков |
| ID типа | 1–64 ASCII-байта, `[a-z0-9_.-]+` |
| Логический бюджет snapshot | 8 MiB |
| Логический бюджет batch | 2 MiB |

Для одинакового подсчёта предложить `snapshot: 32 + 24*число чанков + Σ(32 + длина ID)` и `batch: 64 + 24*число чанков + 28*число removals + Σ(32 + длина ID в upserts)`; считать в `long` с проверкой переполнения. Это **условная стоимость**, а не реальный размер Java-объектов или сетевого пакета. Проверять размеры до копирования и не допускать недопустимых ID или пересечений. При превышении — fail-closed для полного состояния, снять подмены, закрыть подписку, сообщить предел и применить backoff; не усекать. Если snapshot слишком велик постоянно, требуется настройка предела либо новая поддержка безопасной постраничной синхронизации — бесконечные переподключения не помогут. Потребительские лимиты сами по себе не ограничивают память, уже выделенную источником: ограничения/пагинацию на стороне источника нужно внедрить отдельно и проверить нагрузкой.

`unknown` — множество затронутых чанков, по которым визуальное состояние более не считается достоверным. Отсутствие чанка в `Snapshot.knownChunks` тоже означает unknown, не пустой чанк. Известный пустой чанк находится в `knownChunks`, но не имеет entries. Обновление поля `unknown` и `removals` происходит в одном batch; все подмены затронутых клиентом чанков нужно снять без загрузки. Для уже неизвестных чанков повторная инвалидация может не создать нового batch. `Batch.reason` может быть `PISTON`, `PLACE`, `REMOVE`, `PRIME`, `RECONCILE` и т. д., при этом `unknown` всё равно может быть непустым: обрабатывайте поля, не только причину. `known` содержит чанки, которые стали известными; последующие upserts относятся к данным соответствующего batch.

Разница между состоянием и реестром: инвалидация визуала не удаляет тип из файла HyperTNT. Позиции: UUID мира и абсолютные целочисленные x/y/z; координаты чанка вычисляются `x >> 4`, `z >> 4` (корректно для отрицательных значений). Для предметов и установленного блока это независимые механизмы.
