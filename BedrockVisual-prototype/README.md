# Предложение протокола визуализации HyperTNT ↔ ядро

**Для согласования с разработчиком ядра.** Это автономный прототип контракта и модели данных, а не готовая интеграция. Он не загружается плагином и не передаёт пакеты Geyser. Никаких новых обязательных зависимостей ядра в HyperTNT нет. Предложенные имена классов и методов не считаются API ядра. Не устанавливать на рабочий сервер.

## Предлагаемый контракт

Источник истины — реестр HyperTNT. Ядро получает только проверенное представление и рисует клиентам, не меняя физический блок, взрывы, редстоун и защиты. Идентификация: `(UUID мира, x, y, z) → ID типа TNT` (базовый ID `tnt`, остальные — `tnt_fire`, `tnt_obs`, `tnt_heavy`, `tnt_explosive`, `tnt_poseidon`). Обычный TNT не попадает в реестр.

1. Каждое время жизни источника имеет новый случайный `epoch`. В нём каждое **изменение визуального представления** получает последовательный `revision`, общий для всех чанков. Одинаковое состояние второй раз не публикуется.
2. Подключение атомарно возвращает неизменяемый снимок `(epoch, revision, карта типов, множество проверенных чанков)` и подписку, в которой будут все изменения **строго после** этого revision. Источник принимает несколько независимых подписчиков. В прототипе подписка читается через `poll()`, без вызовов внешнего кода под блокировкой. Это форма для согласования, ядро может предложить другой механизм с теми же гарантиями.
3. Чанк, отсутствующий в множестве проверенных, — **неизвестен**, а не гарантированно пуст. Пока нет успешной проверки, ядро не должно рисовать тип по старым сведениям. Для загруженного чанка проверка сверяет снимок реестра с миром в основном потоке сервера. Проверенные записи и статус чанка публикуются одним изменением. Исключение проверки делает чанк неизвестным, сохраняя реестр на диске; при успешной повторной проверке вид восстанавливается. Нельзя синхронно загружать все чанки только ради визуала.
4. `chunkSnapshot` отдаёт снимок одного чанка с epoch/revision. Потребитель буферизует поток общих изменений и применяет снимок только в корректном порядке: никогда не перезаписывает им более новое состояние. Подключение с глобальным снимком и потоком не требует отдельного snapshot для каждого загруженного чанка; отдельный снимок — для resync/обслуживания.
5. После подтверждённых изменений плагин публикует **атомарный пакет** `upserts` и `removals` с причиной (установка, удаление, поджог, замена, поршень, сверка). Удаление при поджоге описывает исчезновение установленного блока; отдельное отображение подожжённой сущности в этом протоколе ещё не реализовано. Поршень публикует все затронутые координаты одним revision, включая несколько блоков и границу чанка. `changeOrInvalidate` под одной блокировкой либо отправляет полный пакет, либо, если хотя бы один затронутый чанк неизвестен, помечает **все** затронутые чанки неизвестными одним пакетом; для остальных случаев есть атомарный `invalidateChunks`. Вызывающий обязан передать полный набор затронутых чанков, включая чанки, где двигаются только обычные блоки. Пакет unknown убирает только визуальные записи, не записи реестра; далее нужна их проверка и повторная публикация.
6. Отменённые события не публикуются. Изменения применять после обработки обычных приоритетов отмены и с учётом известных ограничений `MONITOR`. Если другой плагин меняет состояние события на позднем MONITOR или мир непосредственно меняется без Bukkit-событий, обычный Bukkit API сам по себе не гарантирует полного наблюдения. Не заявлять полную совместимость: нужен проверенный post-commit hook ядра или отдельная стратегия сверки. Для прямого изменения `TNT → обычный TNT` проверка одного `Material.TNT` не способна доказать замену; необходимо сотрудничество инициатора, внешний достоверный журнал изменений или отметить состояние неизвестным.
7. Очередь подписчика ограничена. При переполнении подписка возвращает `RESYNC_REQUIRED`, прекращает выдачу частичных данных; потребитель сначала убирает все старые визуальные подмены, отписывается и заново подключается, получая новый снимок. При потере соединения, разрыве последовательности, несовпадении epoch или сбое обработчика также нужен полный resync. Закрытие источника даёт `CLOSED`; ядро обязано убрать все связанные визуальные подмены, освободить подписку и ждать нового подключения. Это должно работать только с известными клиенту, уже загруженными/отслеживаемыми координатами, без загрузки серверных чанков. Новый процесс источника получает новый epoch. Порядок глобальный, фильтрация чанков — уже после контроля ревизии; при начале отслеживания чанка нужен актуальный снимок, согласованный с потоком. Прототип не может сам гарантировать своевременную обработку сигнала: настоящий адаптер ядра должен обеспечить доставку/проверку отключения и таймаутов.
8. Данные снимков и пакетов неизменяемые. Адаптер не должен делать тяжёлую работу и сетевой ввод/вывод под блокировкой реестра. Проверка мира и взаимодействие с Bukkit выполняются только в допустимом потоке; управление backpressure и состоянием сессии должно учитывать требования конкретного ядра.

## Что уже сделано / что ещё нет

`src/.../VisualFeed.java` — отдельная многопоточная in-memory модель очередей и снимков. Тест `test/.../VisualFeedTest.java` моделирует подключение, снимки и unknown-чанки, пакет поршня, поджог, переполнение очереди, отключение/повторное подключение, новую эпоху и гонку подключения с обновлением. Добавлены атомарная инвалидация набора чанков и имитация очистки подмен у клиента, который отслеживает только видимые чанки. [Автотест прошёл](https://github.com/gulp-tech/shieldyblocks/actions/runs/43743129560), в том числе в многопоточной модели наблюдатель не увидел частичную инвалидацию. Тест не запускает сервер или клиента и не проверяет настоящие события отмены: отсутствие вызова лишь моделирует отмену.

Адаптера к `TntRegistry`, публикации реальных событий, проверки изменённых другими плагинами блоков, API ядра, сетевых пакетов, отрисовки в Bedrock и интеграционных тестов **пока нет**. Сначала необходимо согласовать контракт с разработчиком ядра; затем подключить адаптер на тестовой копии и проверить настоящие чанки, отмены, поршни, перезапуск, WorldGuard/ShieldyBlocks и нескольких Bedrock-клиентов. Не сообщать об игровой совместимости до таких тестов.
